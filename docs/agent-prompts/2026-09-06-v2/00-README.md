# Operix 워크트리 에이전트 프롬프트 v2

작성일: 2026-09-06. 작성에 참고한 Operix 커밋: `0bf3d370d021`.
이 커밋은 작성 근거이며 실행 시 강제할 기준은 아니다. main-pc의 실제 저장소·의존성·지침을 먼저 확인하고 통합 담당이 정한 기준에서 시작한다.

## v2 변경 이유

UI 에이전트가 승인된 UI 변경에 맞춘 기존 E2E 기대 문구 한 줄을 패치로 준비했지만, 공용 파일 배정이 없다는 이유로 작업을 중단한 사례를 반영했다. v1의 파일 단위 조율 규칙을 구체화해, 코드 담당이 자기 역할의 변경에 직접 필요한 최소 테스트 동기화를 조건에 맞춰 자율 적용할 수 있도록 했다. 원본 `2026-09-06/`의 v1 파일은 보존한다.

v2는 다른 에이전트의 같은 테스트 변경 여부, 기대 문구와 실제 UI 의도의 일치, 기존 검증 강도의 보존, 전후 검증과 인계를 요구한다. 실제 같은 테스트·hunk의 중복과 제품 정책·API 계약·인증/권한 모델·DB 스키마·의존성 변경은 계속 조율한다. docs-sync는 통합 후 문서 전용으로 실행한다. 프롬프트 개정과 앱 검증은 구분하며, 이번 UI 사례의 후속 적용·검증 기록은 아래 재개 안내에서 확인한다.

각 프롬프트는 공통 계약을 포함하므로 **해당 파일 전체를 역할별 에이전트의 첫 메시지에 붙여 넣으면 된다.** `00-README.md`를 별도로 붙일 필요는 없다. 별도 에이전트 유형이나 특정 모델 설정도 요구하지 않는다.

특정 화면·버그·보안 이슈가 있으면 프롬프트 아래에 추가한다. 없어도 실제 코드와 동작을 조사해 담당 범위에서 진행하도록 작성했다. 가능한 경우 작업 시작 메시지에 기준 커밋, worktree 경로, 담당 이슈, 조율할 통합 담당을 함께 알려준다.

프롬프트 작성·전송은 실제 UI·보안·버그 수정이나 앱 검증을 실행한 것이 아니다. 각 에이전트의 작업은 파일을 전달해 실행할 때 시작된다.

## 실행 순서

1. 통합 담당 한 명을 정한다. 사용자 본인이나 별도 조정 에이전트가 맡을 수 있다. 네 에이전트가 직접 통신할 수 없다면 통합 담당이 `needs-coordination` 요청과 인계 보고를 전달한다.
2. 공통 기준 커밋과 담당 범위를 고정한다. 미커밋 변경은 새 worktree에 자동으로 포함되지 않으므로 사용자의 기존 작업을 어떻게 반영할지 먼저 확인한다. 자동 stash/reset을 사용하지 않는다.
3. UI·보안·bug-fix용 worktree에서 각각 실행한다. 아래 기본 소유권과 최소 테스트 동기화 조건 안에서는 병렬 수정한다. 그 밖의 공용 코드·설정 변경이나 실제 중복 수정은 통합 담당이 범위·순서를 조율하거나 선행 작업을 통합한 뒤 후속 작업을 갱신한다.
4. 통합 담당이 결과와 검증 증거를 읽고 의존성 순서에 따라 하나씩 통합한다. 인증·API 계약 등 다른 변경의 전제가 되는 수정을 먼저 반영한다. Git 충돌이 없더라도 기능이 함께 동작하는지 확인한다.
5. 통합 기준에서 typecheck·단위/DB·build·필요한 E2E를 실행한다. 각 브랜치의 통과 결과만으로 최종 통과를 선언하지 않는다.
6. 검증된 통합 커밋에서 docs-sync worktree를 만들거나 기존 docs-sync worktree를 통합 담당이 안전하게 갱신한다. 세 역할의 인계 보고와 검증 기록을 전달하고 `04-docs-sync.md`를 실행한다.
7. 문서 변경을 검토·통합하고 링크와 기록의 정확성을 확인한다. push·배포는 별도의 사용자 지시에 따른다.

## 기본 파일 소유권

| 소유자 | 직접 수정 범위 |
| --- | --- |
| UI | `src/components/**`, `src/app/globals.css`, 페이지·레이아웃·화면 상태의 표현 계층 |
| 보안 | `src/lib/auth.ts`, `src/lib/policy.ts`, `src/lib/http.ts` |
| bug-fix | `src/lib/records.ts`, `dates.ts`, `jobs.ts`, `catalog.ts`, `details.ts`, `overview.ts` |
| docs-sync | `README.md`와 관련 최신 가이드. 과거 감사 기록·에이전트 지침은 임의 변경 제외 |
| 코드 담당의 최소 테스트 동기화 | 승인된 역할 변경에 직접 필요한 기존 테스트의 기대 문구·label·selector·동등 assertion. 아래 조건 충족 시 별도 파일 배정 없이 적용 |
| 조율 필요 | 미배정 공용 코드·설정 변경, 실제 같은 테스트·hunk의 중복, 제품 정책·API·인증/권한 모델·DB 스키마·의존성 계약 변경. 주요 경로는 `src/lib/validation.ts`, `sheets.ts`, `db.ts`, `src/app/api/**`, 설정·잠금·DB·실행/배포 스크립트·CI |

이는 출발점이다. 예를 들어 API 수정이 새로 필요하면 통합 담당이 관련 변경 범위를 배정한다. 공용 파일 전체를 수정 금지 대상으로 취급하지 않는다. 이미 승인·배정된 변경은 그 범위에서 진행하며, 코드 담당의 최소 테스트 동기화에는 다음 조건을 적용한다.

1. 자기 역할의 승인된 변경에 직접 필요한 최소 diff인지 확인한다. 기대값 수정은 승인된 변경 의도와 재현 결과로 뒷받침한다. 특히 UI 기대 문구는 UI 변경 의도와 실제 동작이 일치하고 기존 기대값만 오래되었다는 증거가 있어야 한다.
2. 관련 worktree의 status·기준 대비 diff를 읽기 전용으로 확인하고 최근 인계가 있으면 함께 대조해 다른 에이전트가 같은 테스트를 수정 중이지 않음을 확인한다. 같은 파일의 별개 테스트 변경만으로 파일 전체를 잠그지 않는다. 실제 중복은 해당 테스트·hunk만 조율한다. 상태에 접근할 수 없다면 부족한 정보만 요청하고 다른 독립 작업을 계속한다.
3. 자기 worktree에서 적용 전 실패와 적용 후 결과를 검증한다. assertion 삭제·skip·과도한 정규식·selector·오류 무시로 검사를 약화하거나 실제 동작 오류를 숨기지 않는다.
4. 변경 이유, 중복 확인 근거, 전후 명령·결과를 통합 담당과 docs-sync에 인계한다. 역할별 새 테스트도 DB 상태를 공유하는지 확인한다.

## 기존 에이전트 재개용 지시문

기존 역할 에이전트에게 해당 v2 프롬프트와 함께 아래 내용을 붙여 넣는다. 새 worktree에서 작업을 다시 시작하거나 기존 성과를 지울 필요는 없다.

```text
기존 역할 작업을 현재 전용 worktree에서 이어서 진행하세요. v2의 최소 테스트 동기화 규칙을 적용합니다. 승인된 역할 변경에 직접 필요한 기대 문구·label·selector·동등 assertion 수정은 다른 에이전트가 같은 테스트를 변경 중이지 않음을 확인한 뒤 별도 파일 배정 없이 자율 적용하세요. 준비한 패치는 현재 HEAD·diff·인계 기록과 대조해 미반영인 경우에만 타당성을 확인한 뒤 적용하세요. 이번 UI 사례의 수정 커밋 e683bd5가 이미 반영되어 있으면 같은 패치를 중복 적용하지 마세요. 문구 수정은 의도된 UI와 실제 동작이 일치한다는 증거를 먼저 확인하세요. 테스트를 약화하거나 실제 오류에 기대값을 맞추지 말고 적용 전후와 관련 회귀를 검증해 인계하세요. 그 밖의 새 공용 코드·설정 변경, 실제 같은 테스트·hunk 충돌, 제품 정책·API·인증권한·DB 스키마·의존성 계약 변경은 구체적으로 조율하세요. 지정 부재나 응답 대기만으로 이미 허용된 가역적 로컬 작업을 blocked로 끝내지 마세요. 재개 후 현재 HEAD와 검증 증거를 확인해 실제 active goal 상태를 상위 규칙에 따라 정직하게 갱신하고, 필수 작업·검증이 남으면 complete로 표시하지 마세요. docs-sync는 통합 후 문서 전용 범위를 유지하세요.
```

이번 UI 사례의 worktree는 `/home/ubuntu/.herdr/worktrees/Operix/ui-update`다. 통합 담당의 후속 검증 보고에 따르면 기존 UI 커밋 `ed38c44`에서 격리 DB·포트 `3111`로 기대 문구 실패를 재현한 뒤 `test-results/ui-improve/shared-e2e-expected-copy.patch`의 한 줄 변경을 적용했고, 전체 `e2e/operix.spec.ts`가 `11/11` 통과했다(종료 코드 0, 49.6초). 로컬 수정 커밋은 `e683bd5fdf65abd0e51519704c0a051897c6b3c1`이며, 검증 인계는 해당 worktree의 `test-results/ui-unblock-20260906/handoff.md`에 있다. 이 기록은 해당 커밋의 검증 결과이며 이후 변경의 성공까지 의미하지 않는다.

재개 시 현재 HEAD·diff·위 인계 기록을 직접 확인한다. `e683bd5`가 이미 반영되어 있으면 중복 적용하지 않고 남은 작업과 검증 여부를 판단한다. 패치가 미반영이면 실제 파일에서 보고된 `e2e/operix.spec.ts:362`의 대응 구간을 다시 찾아 타당성을 확인한 뒤 적용·검증한다. 외부 UI 에이전트 세션의 기존 goal 차단 상태는 통합 담당의 이번 로컬 조치로 변경되지 않았으므로, 재개한 에이전트가 현재 증거를 확인하고 상위 goal 규칙에 따라 상태를 갱신한다.

## main-pc에서 worktree를 준비하는 예시

기존 worktree가 있다면 재사용한다. 아래는 Windows PowerShell에서 **Operix 저장소 루트**를 현재 디렉터리로 둔 경우의 예시다. 같은 이름의 경로·브랜치가 있으면 다른 이름을 사용한다. 명령이 실패하면 원인을 확인하고 실패한 생성에 기대어 다음 작업을 시작하지 않는다.

```powershell
git status --short
git worktree list
$operixBase = (git rev-parse HEAD).Trim()
git worktree add -b feat/operix-ui-20260906 ../Operix-ui-20260906 $operixBase
git worktree add -b fix/operix-security-20260906 ../Operix-security-20260906 $operixBase
git worktree add -b fix/operix-bugs-20260906 ../Operix-bugs-20260906 $operixBase
```

각 디렉터리를 해당 에이전트의 작업 경로로 지정하고 일치하는 프롬프트를 전달한다. `.env`, `node_modules`, `.next`, DB·업로드 자료는 Git worktree 생성으로 복사되지 않으므로 에이전트가 전용 로컬 환경을 준비하도록 한다.

docs-sync는 코드 통합과 검증이 끝난 뒤, **검증된 통합 커밋을 checkout한 관리 디렉터리**에서 다음처럼 만든다.

```powershell
$operixIntegrated = (git rev-parse HEAD).Trim()
git worktree add -b docs/operix-sync-20260906 ../Operix-docs-20260906 $operixIntegrated
```

docs-sync 시작 메시지에 `$operixIntegrated`의 실제 값과 통합 완료 사실, 세 역할의 검증·문서 인계 보고를 함께 제공한다. 이 예시는 worktree 준비만 수행하며 브랜치 병합이나 배포를 실행하지 않는다.

## 환경 분리와 완료 판단

- `PORT`와 `APP_URL`을 일치시키고, 각 worktree에 전용 `.env`, DB, 업로드·테스트 산출물 경로를 둔다. 제안 포트가 사용 중이면 다른 포트를 사용한다. 운영 자격증명을 복제하지 않는다.
- `npm run setup:local`은 기존 `.env`를 보존한다. 명령 실행만으로 안전한 전용 설정이 되었거나 포트가 변경되었다고 가정하지 않는다.
- 새 환경에서 기본 Playwright 브라우저를 사용하려면 `npx playwright install chromium`으로 준비한다. 별도 브라우저를 사용하는 경우 경로와 플랫폼 호환성을 확인한다.
- 현재 E2E는 `E2E_START_SERVER=1`일 때 `npm run start`를 실행하므로 사전 빌드·전용 가상 데이터 준비가 필요하다. `TEST_DATABASE_URL`을 쓰는 DB 테스트와 `DATABASE_URL`/PGlite를 쓰는 앱/E2E 환경도 구분한다.
- 에이전트 결과의 `complete`는 맡긴 범위와 필수 검증을 완료했다는 뜻이다. `partial`, `needs-coordination`, `blocked`가 있으면 그 이유와 남은 작업을 확인한다. 공용 파일의 지정 부재나 답변 대기만으로 이미 허용된 가역적 작업을 중단하지 않되, 실제 active goal의 상태 변경은 상위 규칙을 따른다. 중단을 피하려고 미완료 작업을 `complete`로 표시하지 않는다. 결함을 찾지 못한 조사도 범위·한계를 정직하게 보고하도록 했다.
- 검증하지 않은 성공, 정적 분석만으로 확정한 취약점, 자동 검사만으로 선언한 접근성 준수, 과거 테스트 수치를 현재 결과로 재사용하는 것을 금지했다.

## 파일 무결성

압축에는 위 Markdown 파일 다섯 개와 `SHA256SUMS.txt`가 들어 있다. 파일을 수정하지 않았다면 해당 해시로 내용을 비교할 수 있다. PowerShell에서는 `Get-FileHash -Algorithm SHA256 .\01-ui-improve.md`처럼 확인한다.
