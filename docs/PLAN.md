# Operix ERP 개발 계획 v0.1

상태: 착수 전 계획 보존본. 현재 결과는 [검증 기록](VERIFICATION.md) 참조.

대상 저장소: [happyaspic-byte/Operix](https://github.com/happyaspic-byte/Operix)

고객사, 설치 자산, 계약, 점검, 장애 대응 이력을 한곳에서 연결하는 사내 ERP를 구축한다. 첫 실사용 버전을 완성한 뒤 영업·구매·재고·재무 업무로 확장한다.

## 첫 버전의 업무 목표

1. 고객사를 열면 사업장, 담당자, 설치 장비, 계약 현황, 최근 점검과 미해결 장애를 함께 확인한다.
2. 자산 ID나 장비명으로 검색하면 사양, 구성요소, VM, 계약, 작업 이력과 문서로 바로 이동한다.
3. 지원·계약 만료와 점검 예정·지연 업무를 담당자가 놓치지 않도록 대시보드와 앱 알림으로 안내한다.
4. 현장에서 점검 결과, 사진과 조치 내용을 입력하고 같은 기록으로 작업 보고서를 만든다.
5. 담당자가 바뀌어도 과거 상태, 관찰 근거와 후속 조치를 이어받을 수 있다.

첫 시범 운영은 고객사 한 곳과 사업장 한 곳의 전체 업무 흐름으로 검증한다. 검증용 장비는 서로 다른 구성 유형을 포함해 선정한다.

## 자산과 계약을 설계할 때 지킬 기준

### 제품별 구성

장비를 모두 같은 형태로 억지로 맞추지 않고 시스템, 구성요소, 가상화 계층을 구분한다.

| 관리 대상                   | 모델링 방향                                                               |
| --------------------------- | ------------------------------------------------------------------------- |
| everRun 시스템              | 시스템 자산 ID와 Node0·Node1, VM, 인터페이스를 연결                       |
| ztC Edge 시스템             | 논리 시스템과 해당 제품 구성의 노드·VM을 연결                             |
| ztC Endurance 시스템        | 하나의 시스템에 CMA·CMB 등 구성요소를 연결하고, 가상화 환경은 별도 기록   |
| 일반 서버·네트워크·스토리지 | 공통 자산 필드에 제품 유형별 항목을 추가                                  |
| VM                          | 소속 가상화 시스템, VM명, 역할, OS, vCPU, 메모리, 디스크, 네트워크를 기록 |

CMA·CMB를 독립적인 고객 자산 두 대로 중복 집계하지 않는다. 부품 교체 시 시스템 자산 ID는 유지하고 구성요소의 시리얼과 교체 이력을 변경한다.

FT·HA 같은 보호 모드는 적용되는 시스템·VM 계층에 기록한다. 미확인 항목은 미확인 상태로 유지한다. 제품별 허용 사양과 운용 제한은 해당 버전의 제조사 자료로 별도 검증한다.

### 필수 정보와 단계적 보완

최초 자산 등록에는 고객·사업장, 자산명, 제품 유형, 내부 담당자와 내부 식별자를 요구한다. 제조사 자산 ID는 알면 입력하며, 누락되어도 임시 등록할 수 있다.

자산 ID, 시리얼, 모델, 버전, 설치일, IP, 가상머신과 사양은 수집되는 순서대로 보완한다. IP에는 관리·업무 등 용도와 네트워크 구분을 함께 기록한다. 서로 다른 사업장에서 동일한 사설 IP를 사용할 수 있으므로 IP를 전사 고유 식별자로 쓰지 않는다.

중요한 상태·사양에는 확인 일시, 입력자와 자료 출처를 남긴다. 장비 목록의 상태는 최근 확인 상태로 표시하고 최신 확인 시간을 함께 보여 준다.

### 기간과 갱신

회사 유지보수 계약 기간, 제조사 지원 기간, 제품 사용권 기간은 별도 항목이다. 제조사 지원 종료를 제품 사용권 종료로 간주하지 않는다.

기간이 없는 값은 미확인과 무기한을 구분한다. 계약의 날짜는 업무 날짜로, 작업과 감사 이력은 시각으로 보관한다. 시각은 UTC로 저장하고 기본 화면은 한국시간으로 표시한다.

만료 안내 기본안은 90일·60일·30일·7일 전과 만료 당일이다. 같은 대상·만료일·구간의 알림은 중복 생성하지 않는다. 갱신으로 종료일이 변경되면 이전 예정 알림을 정리한다.

### 기록의 신뢰도

장애 원인은 관찰 사실, 내부 추정, 제조사 확인을 구분한다. 내부 분석을 공식 제조사 진단으로 표시하지 않는다. 완료 보고서는 당시의 내용을 고정해 보관하고 이후 수정은 새 버전으로 남긴다.

## 핵심 데이터 관계

| 관계                  | 설계 기준                                                      |
| --------------------- | -------------------------------------------------------------- |
| 고객사 → 사업장       | 한 고객사가 여러 사업장을 가질 수 있음                         |
| 사업장 → 시스템 자산  | 한 사업장에 여러 시스템 자산이 설치됨                          |
| 시스템 → 구성요소·VM  | 제품 구조에 맞게 세부 구성을 연결                              |
| 계약 ↔ 자산           | 한 계약에 여러 자산을 포함하고 한 자산의 여러 계약 기간을 보존 |
| 지원·사용권 → 자산    | 종류와 기간을 독립적으로 관리                                  |
| 점검 계획 → 점검 실행 | 반복 규칙과 회차별 실제 결과를 구분                            |
| 장애·작업 ↔ 자산      | 여러 장비가 관련된 장애도 연결 가능                            |
| 작업 → 기록·문서      | 변경 시점, 근거 자료, 조치 결과, 보고서를 함께 보존            |

고객·자산·계약의 내부 식별자는 변경 가능한 이름과 분리한다. 이력이 있는 주요 자료는 보관 상태로 전환하고, 관련 기록이 있는 대상을 잘못 삭제해 이력이 끊기지 않도록 한다.

## 권한 초안

| 역할             | 주요 권한                                                      |
| ---------------- | -------------------------------------------------------------- |
| 시스템 관리자    | 임직원 계정·역할·환경 설정·데이터 관리                         |
| 대표·업무 관리자 | 전사 현황 조회, 업무 배정, 계약 관리, 완료 보고서 확정         |
| 기술지원         | 업무에 필요한 고객·자산 조회, 담당 점검·장애 기록, 보고서 초안 |
| 영업·관리        | 고객·계약 등록 및 갱신 관리, 점검·지원 결과 조회               |
| 조회 전용        | 허용된 자료 열람                                               |

금액 열람, 전체 자료 내보내기, 내부 네트워크 정보 열람, 삭제·보관 처리는 각각 별도 권한으로 관리한다. 처음부터 사용자가 임의로 역할을 생성하는 복잡한 화면을 만들기보다 기본 역할과 제한된 권한 설정으로 시작한다.

계정은 관리자 초대로 발급하고 퇴사·정지 시 세션을 회수한다. 로그인 후 메뉴 이동, 새로고침, 직접 URL 접속과 세션 만료를 함께 검증한다.

데이터 읽기·변경·파일 다운로드 때 서버에서 권한을 확인한다. 권한 검증을 데이터 접근 지점에 집중하는 방향은 [Next.js 공식 인증 가이드](https://nextjs.org/docs/app/guides/authentication)를 참고한다.

## 화면 방향

데스크톱에서는 표와 필터를 중심으로 빠르게 조회·수정하게 하고, 휴대폰에서는 현장 점검·사진 첨부·작업 기록을 편하게 입력하게 한다.

- 기본 배경: 밝은 회색 계열, 콘텐츠 영역: 흰색, 강조색: 한 가지 주 색상.
- 목록: 검색, 저장 가능한 필터, 정렬, 필요한 열 선택.
- 고객 상세: 개요, 사업장·담당자, 자산, 계약, 점검·장애, 문서.
- 자산 상세: 개요, 구성·VM, 네트워크, 계약·지원, 작업 이력, 문서.
- 상태: 색상과 글자 표시를 함께 사용.
- 입력 폼: 필수 항목을 최소화하고 오류를 해당 항목 가까이 표시.
- 업무용 화면의 로딩·빈 결과·권한 없음·오류 상태를 함께 설계.
- 실시간 장비 수집을 추가하기 전까지 상태 표시에는 확인 일시를 명시.

첫 화면 설계 대상은 대시보드, 고객 상세, 자산 상세, 점검 입력, 장애 상세의 다섯 화면이다.

## 기술·운영 구성 제안

| 구성              | 제안                                          | 목적                                         |
| ----------------- | --------------------------------------------- | -------------------------------------------- |
| 웹·서버           | Next.js App Router + TypeScript, Node.js 실행 | 화면과 업무 로직을 한 프로젝트에서 관리      |
| 애플리케이션 구조 | 업무 영역별 모듈로 구분한 단일 애플리케이션   | 고객·자산·계약의 공통 규칙 유지, 단계적 확장 |
| 데이터베이스      | PostgreSQL                                    | 고객·자산·계약 관계와 변경의 일관성 관리     |
| 인증              | 유지보수되는 인증 라이브러리와 서버 세션      | 계정·세션 수명과 권한 관리                   |
| 첨부 파일         | 비공개 영속 파일 저장소, DB에 메타데이터 보관 | 컨테이너 교체 후에도 자료 유지               |
| 일정 처리         | 같은 코드베이스의 별도 작업 프로세스          | 만료 안내·반복 점검 생성을 웹 요청과 분리    |
| 배포              | Docker Compose                                | 웹·DB·작업 프로세스의 구성 재현              |
| 접속              | HTTPS 역방향 프록시, 사내망·승인된 VPN        | 내부 업무 시스템의 접근 범위 관리            |
| 개발 검증         | GitHub Actions에서 빌드·핵심 테스트           | 변경 시 업무 흐름 손상 발견                  |
| 운영              | 상태 점검, 오류 기록, 백업·복구 절차          | 장애 확인과 복구 가능성 확보                 |

Next.js는 Node.js 서버와 Docker 배포를 지원한다. 사내 Ubuntu 운영을 선택한 상황에서 이 구성을 권장한다. [Next.js 배포 문서](https://nextjs.org/docs/app/getting-started/deploying)

역방향 프록시와 애플리케이션 실행 환경은 함께 구성한다. [Next.js 자체 호스팅 가이드](https://nextjs.org/docs/app/guides/self-hosting)

Docker Compose는 여러 컨테이너의 서비스를 하나의 구성으로 정의·관리할 수 있다. [Docker Compose 공식 문서](https://docs.docker.com/compose/intro/features-uses/)

사용 라이브러리, ORM, 인증 제품과 버전은 기반 설계 단계에서 유지보수 상태·호환성을 확인해 고정한다. 호스팅 서비스에 종속된 기능을 필수 구성으로 넣지 않는다.

작업 프로세스의 예정 업무·실행 결과는 DB에 기록한다. 중복 실행 방지, 재시도와 실패 표시를 포함한다. 첫 버전 알림은 앱 내부에서 제공하고 메일·메신저 발송은 후속 연동으로 둔다.

## 공개 저장소와 운영 데이터

현재 Operix는 공개 저장소다. GitHub에는 코드, 문서와 가상 샘플 데이터를 저장하고 실제 고객 자료, 내부 IP, 계정, 계약서, 지원 로그와 DB 백업은 사내 운영 저장소에서 관리한다.

장비 비밀번호를 일반 자산 메모에 저장하는 기능은 범위에 넣지 않는다. 자격증명 관리가 필요하면 별도 비밀 저장소를 연결하는 설계로 확장한다.

문서·지원 로그는 로그인과 해당 자료 열람 권한을 확인한 후 제공한다. 파일 형식·크기 제한, 저장 경로 처리, 업로드 실패 처리를 설계하며 지원 로그 전체를 자동 수집하는 기능은 이번 범위에 포함하지 않는다.

저장소 공개 여부와 사내 ERP의 접속 공개 여부는 별개의 설정으로 관리한다.

## 기존 자료 이관

1. 사용자가 제공하는 대표 자산표·계약표·점검 양식을 기준으로 필드 대응표를 만든다.
2. 고객사·사업장 명칭과 제품 유형을 먼저 정리하고 기존 원문과 출처를 보존한다.
3. 가져오기 전에 행별 오류, 중복 후보, 생성·수정 예정 내용을 보여 준다.
4. 사용자가 매핑과 결과를 확인한 뒤 한 배치를 반영한다.
5. 반복 가져오기 시 같은 자산을 중복 생성하지 않도록 내부 ID와 검증된 외부 식별자를 활용한다.
6. 반영 전후 건수, 실패 행과 변경 내역을 기록한다.

불명확한 회사명, 자산 ID와 만료일은 추측해 합치지 않는다. 실제 원본 자료가 확보되기 전까지 가상 데이터로 설계와 기능을 검증한다.

## 단계별 개발 계획

| 단계                | 주요 작업                                                                 | 완료 기준                                                        |
| ------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 0. 상세 설계        | 필드 사전, 관계 모델, 권한표, 5개 핵심 화면, 데이터 샘플, 기술 결정       | 고객 한 곳의 자산·계약·점검·장애 흐름을 설계로 설명할 수 있음    |
| 1. 공통 기반        | 저장소 초기 구성, 로그인·세션, 역할·권한, 공통 화면, DB 변경 관리, Docker | 로그인 이후 메뉴 이동·새로고침 정상, 권한 없는 서버 요청 차단    |
| 2. 고객·자산        | 고객사·사업장·담당자, 시스템·구성요소·VM, 검색·필터·이력                  | 장비 등록부터 고객 화면에서 이력 확인까지 연결, 중복 식별자 검증 |
| 3. 계약·일정        | 계약·제조사 지원·사용권, 갱신 관리, 반복 점검, 앱 알림                    | 만료·미확인·무기한 구분, 날짜 경계와 중복 알림 검증              |
| 4. 점검·장애·보고서 | 체크리스트, 사진·문서, 작업 기록, 벤더 케이스, PDF                        | 접수부터 조치 기록과 완료 보고서까지 한 흐름으로 완료            |
| 5. 이관·시범 운영   | 표준 양식 가져오기, 제한된 실자료 이관, Ubuntu 설치, 백업·복구            | 시범 업무 완료, 컨테이너 교체 후 자료 유지, 별도 환경 복구 성공  |

1차 개발은 5단계의 완료 기준까지 포함한다. 로그인 화면이나 목록 화면이 표시되는 상태를 실사용 완료로 보지 않는다.

달력 일정은 0단계에서 원본 자료의 양, 실제 사용자 수, 서버 환경과 투입 가능한 작업 시간을 확인한 후 잡는다. 단계별 결과를 검토할 수 있도록 작은 변경 단위로 진행한다.

## 운영 시작 전 검증 기준

| 확인 대상      | 통과 기준                                                           |
| -------------- | ------------------------------------------------------------------- |
| 세션           | 로그인 후 이동·새로고침 정상, 만료·정지 계정의 접근 차단            |
| 권한           | 직접 URL·API·파일 다운로드·내보내기에서도 권한 적용                 |
| 관계·이력      | 고객·사업장·계약·자산 연결과 변경 이력 보존                         |
| 동시 수정      | 다른 사용자의 변경을 알림 없이 덮어쓰지 않음                        |
| 만료·반복 일정 | 날짜 경계, 갱신 후 재계산, 중복 실행·누락 복구 검증                 |
| 가져오기       | 오류 행·중복 후보·재반영을 확인하고 승인한 내용만 반영              |
| 보고서         | 한국어, 긴 내용, 사진, 여러 페이지가 포함된 실제 양식으로 출력 확인 |
| 배포           | 새 컨테이너로 교체해도 DB·첨부 파일 유지, 상태 확인 가능            |
| 복구           | 별도 빈 환경에 DB와 대응 첨부 파일을 함께 복원해 업무 조회 성공     |

백업은 DB, 첨부 파일과 운영 설정의 복구를 함께 다룬다. 논리 백업과 복원은 PostgreSQL의 pg_dump·pg_restore 체계를 기준으로 설계한다. [PostgreSQL 공식 백업 문서](https://www.postgresql.org/docs/current/backup-dump.html)

초기 제안은 일별 백업·30일 보존·운영 서버와 다른 저장 대상이다. 허용 가능한 데이터 유실 시간을 확인한 뒤 빈도를 확정한다. 하루 한 번 백업이면 최악의 경우 약 하루의 변경이 손실될 수 있다. 백업 중 첨부 파일과 DB의 대응 관계를 보존하는 절차도 포함한다.

복구 시간 목표는 실제 복구 시험 결과로 정한다. 애플리케이션 버전 되돌리기와 DB 변경 복구는 별도 절차로 관리한다.

## 후속 확장

| 확장 단계 | 범위                                                       | 기존 기능과의 연결                  |
| --------- | ---------------------------------------------------------- | ----------------------------------- |
| 2차       | 견적·수주·구매·발주·재고·부품 교체                         | 고객·계약·설치 자산을 재사용        |
| 3차       | 비용·매출·정산, 기존 회계 시스템 연계                      | 수주·구매·유지보수 실적 연결        |
| 별도 검토 | 고객 포털, 인사·근태, 메일·메신저, AI 요약, 장비 자동 수집 | 실제 수요와 접근 권한을 확인해 추가 |

각 기능은 기존 고객·자산을 다시 입력하지 않고 참조하도록 확장한다. 고객 포털과 장비 제어·자동 수집은 별도의 접근·운영 설계가 필요하다.

## 상세 설계 단계에서 확인할 자료

지금 추가 답변을 기다려야 하는 항목은 아니다. 각각 필요한 단계에서 실제 자료를 확인한다.

- 임직원 수와 담당 업무, 사용자별 열람 범위.
- 고객·사업장·자산 건수, 대표 자산표·계약표·점검 양식 각 1개.
- Ubuntu 버전, CPU·메모리·디스크 여유, 기존 Docker·Portainer 운영 여부.
- ERP 접속 주소와 VPN 방식, 별도 백업 저장 대상.
- 기존 사내 인증·메일 환경과 문서 보존 기준.

계획 작성 당시 다음 준비 산출물은 메뉴 구조, 필드 사전, 권한표, 핵심 화면 설계였다. 이후 구현·검증 결과와 남은 운영 작업은 검증 기록에 갱신한다.
